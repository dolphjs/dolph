Controllers are responsible for handling incoming HTTP requests and returning responses to the client. In DolphJS, a controller's purpose is to receive specific requests for the application, delegate the complex business logic to **multiple Services**, and return the computed result. The framework is intentionally designed such that a controller acts as an orchestrator for multiple services, rather than just routing to a single service.

## Basic Controller

To create a controller, write a class and use the `@Route` decorator to define the base path.

```typescript
import { Route, Get } from '@dolphjs/dolph';

@Route('cats')
export class CatsController {
    @Get()
    async findAll() {
        return 'This action returns all cats';
    }
}
```

:::note
Return data to send a response, and throw an exception to send an error. Dolph wraps all auto-returned controller values in a standardized JSON envelope:
```json
{
  "success": true,
  "status": 200,
  "message": "Request successful", // "message" uses the return value if it's a string
  "data": { ... } // "data" uses the return value if it's an object/array
}
```

```typescript
@Get('direct')
async returnDirectly(req: DRequest, res: DResponse) {
    // Returning data directly works exactly as it does in NestJS
    return { name: 'Utee' };
    // Automatically sent as: { success: true, status: 200, message: 'Request successful', data: { name: 'Utee' } }
}
```

If you prefer a different response envelope, you can override this behavior globally via the `DolphFactory`:

```typescript
// server.ts
const dolph = new DolphFactory([AppComponent], {
    onResponse: (data, req, res) => ({
        myCustomSuccess: true,
        payload: data,
    }),
});

dolph.start();
```
:::

## Routing

The `@Get()`, `@Post()`, `@Put()`, `@Patch()`, and `@Delete()` decorators tell DolphJS to create an endpoint for this specific HTTP method.

You can also pass path parameters to these decorators.

```typescript
@Get(':id')
async findOne(@DParam('id') id: string) {
  return `This action returns cat #${id}`;
}
```

## Request Payloads

DolphJS provides decorators to extract payloads from the incoming request cleanly.

- `@DBody()`: Extracts the `req.body`.
- `@DParam('name')`: Extracts a specific route parameter `req.params.name`.
- `@DQuery('name')`: Extracts a query parameter `req.query.name`.

### Example with DTOs

If you integrate a validation library like `class-validator`, you can type your `@DBody()` to automatically enforce payload structures (handled in conjunction with middlewares).

```typescript
import { Post, DBody } from '@dolphjs/dolph';

class CreateCatDto {
  name: string;
  age: number;
}

@Post()
async create(@DBody() createCatDto: CreateCatDto) {
  // Pass the DTO to a service
  return this.catsService.create(createCatDto);
}
```

## Status Codes

Responses are `200` unless you choose otherwise. Take the response with `@DRes()` to set a status, set cookies or headers, and still return your data:

```typescript
@Post()
async create(@DBody() dto: CreateCatDto, @DRes() res: DResponse) {
  res.status(201);
  return this.catsService.create(dto);
}
```

To answer with an error, throw one of Dolph's exceptions, like `NotFoundException`.

## Dependency Injection

Controllers rarely execute business logic themselves. Instead, they rely on Services declared alongside them in a `@Component`. DolphJS supports two ways for a controller to receive them.

### Constructor Injection (recommended)

Declare the service as a constructor parameter, and `@Component` resolves and passes it in automatically:

```typescript
@Route('cats')
export class CatsController {
    constructor(private readonly catsService: CatsService) {}

    @Get()
    async findAll() {
        return this.catsService.findAll();
    }
}
```

This is the preferred style going forward — besides reading naturally, it's the form that lets you construct the controller directly in a unit test (`new CatsController(mockService)`) without reaching into the instance by hand. See [Testing](/testing/#tier-2--controller-unit-tests).

### Field Injection

If the controller has no constructor parameters, `@Component` instead defines a property on the instance for every service declared in the same component — named **after the service's class itself**, not a lowerCamelCase alias:

```typescript
@Route('cats')
export class CatsController {
    // The property name must match the class name exactly — DolphJS assigns
    // it as `instance.CatsService`, not `instance.catsService`.
    private CatsService!: CatsService;

    @Get()
    async findAll() {
        return this.CatsService.findAll();
    }
}
```

:::caution
Do **not** instantiate the service manually (`new CatsService()`). Let the Dependency Injection container handle it to ensure singleton state and proper memory management. And regardless of which style you use, do not mix the two on the same class — a controller either takes its services as constructor parameters, or declares them as class-name-matched fields, not both.
:::

## Asynchronous Handlers

By default, DolphJS wraps your controller methods in an asynchronous try-catch block. If an error is thrown within your method, it will be automatically passed to the next global error handler. You do not need to write verbose `try...catch` blocks inside every route!

## Testing Controllers

A controller built with constructor injection (`constructor(private readonly catsService: CatsService)`) can be unit tested the same way as a service — construct it directly with `new` and a mock, no Express involved. See [Testing → Tier 2](/testing/#tier-2--controller-unit-tests) for the full pattern, including how to mock `DRes()` for handlers that write to the response directly.
