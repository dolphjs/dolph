DolphJS 3.1 ships its own HTTP engine. It has no Express and no Fastify underneath — just a lean request pipeline on Node's `http` module — while keeping the promise the framework is built on: **Express middleware works as-is**.

## Switching to the Dolph engine

No packages to install. Set the adapter in `dolph_config.yaml`:

```yaml
adapter: dolph
```

That's the whole change. Your controllers, services, shields, DTO validation and middleware stay exactly as they are. You can also set `DOLPH_ADAPTER=dolph` as an environment variable, which takes priority over the config file — useful for running the same app on all three engines.

If you use `dolph new`, the CLI asks which server to run on and offers `express`, `fastify` and `dolph`.

## Why it exists

The engine exists for the two numbers people actually feel: how fast the app answers, and how much memory it holds while doing it. The same application on all three adapters:

## Express middleware

Unlike the Fastify adapter, the Dolph engine doesn't need a bridge package — middleware runs against the real Node request and response with Express-compatible helpers, so `cors`, `helmet`, `cookie-parser`, `morgan`, `compression`, `response-time`, `method-override`, `hpp` and `express-rate-limit` all work unmodified:

```typescript
new DolphFactory([AppComponent], { middlewares: [cookieParser(), session({ secret })] });
```

Anything middleware sets on `req.payload`, `req.user`, `req.session` or `req.cookies` reaches your handlers, `res.locals` is shared, and `helmet` and `cors` from `dolph_config.yaml` still run first, before the body is parsed.

The `piku` compatibility sample — a medium-sized app running the engine with seven Express packages wired in, one test per compatibility claim — exercises exactly this.

## What's different

- **Express routers:** `DolphRouteHandler` and `express.Router()` need `adapter: express`, exactly as on Fastify. The app stops at startup with a clear error. Use `@Route` controllers instead.
- **Views:** `@Render` works with `ejs`, `pug` and `handlebars` called directly — install your template engine as usual, but no adapter plugin like `@fastify/view` is needed.
- **Runtime:** the engine is built on the `http` module, which Bun implements, so the same adapter runs on Node and on Bun.

## Running it on Bun

Nothing in the adapter changes: install [Bun](https://bun.sh), then start the app with `bun run` instead of `node`. The engine picks up Bun's `http` implementation automatically; Express middleware keeps working the same way.
